# Matt Pocock Skills：把 AI 开发中的访谈、规格与测试变成可重复的方法

**这是一组给编码 Agent 阅读的指令与参考文件，不是新的 AI 模型，也不是一个安装后就自动提高代码质量的平台。你调用某个技能，让 Agent 依照约定方式追问需求、写规格、拆任务、测试或审核。它改善的是工作方法，收益取决于你遇到的问题是否正好需要这套方法。**[1]

资料研究日期 2026-11-04；发行参考 v1.3.2。本文只读取公开内容，不安装或调用这些技能，也不把其中的指令作为本站当前执行规则。

## 1. 先看清：它交付的不是程序，而是行为规范

当你要求 Agent “帮我改审核页面”，最常见的失败未必是模型不会写代码，而是没有问清审核状态、失败行为或谁有权限。技能集合把这些容易跳过的步骤写成可复用文件，让你不必每次临时编一大段过程要求。

仓库当前区分 engineering 与 productivity 等内容，并区分用户显式调用与模型可按任务使用的技能。这种区分是入口和流程设计，不是对全部 Agent 宿主一致行为的保证；实际触发与工具支持仍取决于集成。[1]

读者不需要一口气理解全部技能。最有用的开始方式是先指出自己的失败类型：需求总被误解、测试只走过场，还是交接后背景丢失？先选能约束这一环节的小能力，而不是把安装数量当成熟度。

## 2. 一次完整流程：从模糊要求到可审核改动

举一个应用示例：你希望导入规则时能解释错误。可先通过需求访谈澄清输入、错误分类、用户身份和不能改的行为；再形成规格，确认后拆任务；实施时逐步测试；最后审核差异和验收证据。具体步骤按所选技能与项目情况决定，不是要求每次小改动都跑全套。

官方推荐的 setup 会询问 issue tracker、标签和文档保存位置。这里有实际意义：如果任务和文档被写到错误地方，流程看似完整，团队却找不到主来源。设置集成是为了让产物进入你既有协作方式，而不是自动替换团队治理。[1]

若需求已经很明确，重复访谈可能变成负担。比如只修改一个已确认的文案，不一定值得重新做领域建模和任务拆分。方法应该服务于风险与不确定性，而不是成为每次请求的仪式。

## 3. 几个值得先理解的能力

| 能力方向 | 具体帮助 | 需要你的参与 |
| --- | --- | --- |
| grill / grill-with-docs | 通过追问暴露需求空白，整理术语与决策 | 确认问题优先级，纠正模型的假设 |
| to-spec / to-tickets | 把已对齐的要求变成规格与任务 | 审阅范围、依赖、验收条件与 tracker |
| tdd | 约束先验证行为、再逐步实施 | 明确要测的公共边界，而非让模型自说自话 |
| diagnosing-bugs / review | 固化排查与检查步骤 | 判断复现、证据与风险是否成立 |

v1.3.2 的 TDD 文本强调公共接口行为、先商定测试边界、避免按实现细节耦合的测试，以及一条测试配一小步实现。这不是“写出更多测试”的口号，而是在约束什么才值得测试。[2]

这些约束也有成本：需要花时间确认边界，模型可能增加阅读和往返。指令只能影响过程，不能保证它真的正确运行过测试，产出的执行记录仍需核验。

## 4. 外部评价：认可需求澄清，但不等于整套都该常驻

Reddit 的相关讨论中，有人把规格管理与执行技能分层组合，也有人只保留需求访谈，认为全套过程在新模型上变成额外负担。部分回复还推广自己的工具，因此不能视为无利益关系的统一结论。[4]

这些经验的共同可用部分是：避免同时让两套规划系统争夺主来源；已经稳定的步骤不必再叠一套。它并不能证明某个技能一定提升代码正确率，也不能根据某位用户的模型体验预测你的项目。

MrKeyoor 的资料评估还讨论了访谈本身可能增加注意力成本，以及应核对生成的术语与任务是否符合实际决定。本稿采用其提出的检查问题，不把安装环境大小或一次脚本结果转化为技能效果评分。[5]

本轮没有找到足以支持“整套技能相对基线提升多少”的统一独立证据。技能目录的扫描通过、安装量和好评，可用于发现入口或文本审查线索，不是交付质量的实验证明。

## 5. 与项目说明、手写提示、Superpowers 等路线怎样比较

项目说明文件适合放稳定约束：测试命令、目录规则、术语和禁区。一次性提示适合当前任务的具体要求。技能则适合重复发生的操作方法。三者可以互补，但不应重复写出互相冲突的要求。

同类方法集合可能都包含规划、TDD 和审阅。选择时应比较实际文本规定了什么、何时触发、会写哪些文件、是否调度额外 Agent，而不是简单比较仓库 Star 或技能数量。本轮不运行任何这些集合，所以不评哪套整体更强。

如果你已有成熟的领域协作契约，优先保持它为事实来源；需要补的可能只是访谈、测试或交接中的一个环节。把通用技能替换成业务规则，反而可能丢失真正重要的约束。

## 6. 对你的用途：把“你理解了吗”变成可检查的对齐产物

你对研究站内容反复要求先对齐，正说明需求复述不等于真正理解。借鉴这类方法，可以在写文章前固定读者问题、证据边界与验收样例，再让产物接受同一套检查。这里是方法借鉴，不是说安装本仓库就会自动获得深度研究。

在配置或开发任务中，术语表和决策记录也可能有帮助，例如区分“校验失败”“送审失败”和“执行失败”。但模型记录的术语需要你确认；如果一开始归纳错了，一致使用错误词汇只会让偏差更难察觉。

最合适的产物不是更长的过程报告，而是一份你能审阅的规格、明确的测试边界和与之对应的变更。若这些已有，额外提问与文档应能说明新增价值，否则就应减掉。

## 7. 成本、权限与维护：提示文件也有行为影响

当前仓库 API 识别 MIT 许可；搜索中某些目录仍标未声明许可，说明目录快照会滞后，正式使用应回到当前原仓库核对。代码开放不代表执行技能免费，模型阅读、追问、测试调用和可能的子任务仍消耗资源。

技能内容可能要求写文档、更新 issue、调用工具或形成提交。只因为它是 Markdown 文件，不能认为它没有状态影响。安装前需要审查你会调用的文本，并与宿主工具权限及用户授权保持一致。

v1.3.2 发布记录包含要求先读技能原文再作建议、审核时查找项目标准等修订，说明方法文本本身也会发生有意义的变化。[3] 应固定采用版本，升级时查看关键流程，而不是把第一次读过当成永久审查。

## 8. 最终判断：围绕一种反复失败选技能，而非为了全面而全装

如果你反复遇到“Agent 立刻动手却没理解要求”，访谈和规格方向值得先研究；如果任务对齐但实现不可靠，测试与排查方法更相关。若只是少量明确修改，保留简短任务要求和既有项目标准可能已经足够。

本轮确认了具体指令设计与适用差异，也读到了支持与反对完整流程的用户意见。仍不能证明它提高了你的正确率或降低费用；尤其不能把主张严格工程方法，直接等同于每次都能严格执行。

采用的核心标准应该是：同一项工作是否更少误解、产物是否更可核验、增加的往返是否值得。所有这些效果本轮均未实测。本站也没有安装或执行该仓库的技能。
